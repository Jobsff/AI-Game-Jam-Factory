# 制作人主导的里程碑式多智能体工作流

> 目标不是让更多智能体参与，而是在正确时点使用最合适的角色，并按时交付。

## 1. 先选交付模式

| 模式 | 首要目标 | 审查深度 |
|---|---|---|
| `PROTOTYPE` | 证明想法值得做 | 最低工程卫生与短时试玩 |
| `JAM_DEMO` | 完整、好玩、可演示、按时提交 | 主路径与演示窗口稳定 |
| `VERTICAL_SLICE` | 证明产品潜力和可维护性 | 资源、性能、主要设备开始量化 |
| `COMMERCIAL` | 可长期运行并安全发布 | 完整质量、安全、可靠性与发布门槛 |

本项目比赛阶段默认：`JAM_DEMO`。

## 2. 角色与权力

| 角色 | 负责 | 不负责 |
|---|---|---|
| 制作人 / 主智能体 | 目标、范围、时间、委派、缺陷裁决、最终拍板 | 不把 QA 建议自动变成开发任务 |
| KK3 | 关键决策前的只读审查与实施简报 | 日常写代码、无限架构审计、最终拍板 |
| G53 | 最小实现、根因修复、相关测试 | 重新定义需求、擅自扩范围、独立红队 |
| MM3 | 里程碑前的限时交付阻断检查 | 持续挑刺、直接排期、回归时扩大攻击面 |

## 3. 路由规则

- 默认由主智能体或 G53 直接完成明确的小任务。
- 只有需求含糊、决策昂贵、跨模块或不可逆时才调用 KK3。
- MM3 只在“首次可玩、功能冻结、发布候选”等明确里程碑出现。
- 圆桌只用于高杠杆决策，一轮结束，由制作人拍板。

## 4. 比赛模式（JAM_DEMO）

```text
定题：KK3 一次，15 分钟内收敛范围
开发：G53 持续生产，优先开始→玩法→胜负→重来
首次可玩：MM3 20 分钟阻断检查，最多 5 项
打磨：G53 完成美术、音效、反馈和提交材料
功能冻结：MM3 最终检查 30–45 分钟
返修：只修 P0/P1 和制作人批准的 P2
回归：MM3 只验证已修问题，随后结束
提交：不再开启新审查面
```

比赛缺陷预算：`P0=0`、`P1=0`；P2 不得影响演示主路径；P3 全部进入赛后 backlog。

## 5. 其他项目

- `PROTOTYPE`：KK3 可选，G53 为主，MM3 只做短时 smoke。
- `VERTICAL_SLICE`：KK3 审架构与资源边界，MM3 在版本候选时做更广回归。
- `COMMERCIAL`：由项目明确安全、性能、设备和发布门槛；仍须设置范围、预算和退出条件。

## 6. 强制停止条件

- 每次委派都必须写明：目标、范围、时间预算、问题上限、退出条件。
- 默认只允许一次“修复 → 回归”循环；仍有阻断问题则由制作人选择降级、绕开或 No-Go。
- 回归不得发现新问题后自动续跑；新问题进入下一里程碑或 backlog。
- 距提交不足 12 小时，不做架构重构；不足 6 小时，只处理 P0/P1；不足 2 小时，只处理提交故障。
- ZCode Goal Mode 只用于目标可检查且有使用预算的任务，不用于“找出所有问题”或“做到完美”。

## 7. 最小任务包

```text
DELIVERY_MODE：
当前里程碑与截止时间：
目标与验收：
允许范围 / 禁止范围：
时间预算 / 问题上限：
必须保持不变：
退出条件：
```

## 8. 交接规则

- KK3 → G53：目标、文件边界、不变量、验收、待核验。
- G53 → MM3：可见行为、修改文件、测试证据、高风险假设。
- MM3 → 制作人：最多 5 个可复现问题；不得自行决定全部修复。
- 制作人 → G53：只下发已批准的问题和优先级。

## 9. 制作人对人类的沟通协议

- **三问卡片**：任何要花钱、动代码或开新委派的动作，先用大白话说明——①要做什么（一句人话＋比喻）②做了的好处 ③不做行不行（必须做｜可缓｜可不做＋代价）；能用选择题就不用填空，重要决策上选择项，**确认后再动手**。
- **环节不确定先问**：分不清当前是正式开发还是原型演练时，停下来问人类，不得自行假设。
- **即时上抛**：需要人类决策、凭据或物理操作时，标注【需要你决定】并停，不猜。
- 等待人类裁决时保守处置：不动可能是对方正在写的文件；结论先行，术语随文解释。

最终衡量标准：是否在预算内交付当前里程碑，而不是是否穷尽了所有可能问题。
